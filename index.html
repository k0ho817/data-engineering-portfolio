문제와 설계

프레임워크마다 입력 전처리가 달라지면 학습 방식만 비교하기 어렵습니다. 이미지와 XML 라벨을 매핑하고 224×224 이미지의 PNG 바이트를 Parquet에 저장해 공통 입력으로 사용했습니다.

실행 결과는 rank별 JSONL, 요약 지표, 자원 관측값으로 남겨 CSV와 보고서로 연결했습니다.

다룬 문제

  • Parquet shard별 행 수 차이에 따른 rank별 batch 불균형
  • Ray Data 선읽기로 발생하는 불필요한 입력과 메모리 사용
  • 다중 노드 GPU 배치와 측정 조건의 불일치
  • NVML GPU 식별 오류와 메모리 지표의 해석 차이
설계 판단과 검증 결과

작업에 필요한 만큼 읽기

KubeRay 결과 원장에는 선읽기 27.1k행·3.5GiB가 발생한 진단 실험에서 shard 내부 제한 읽기 적용 후 12행·약 61KiB로 줄어든 기록이 있습니다. 전체 데이터셋이나 모든 학습 작업에 적용되는 절감률로 일반화하지 않았습니다.

측정값의 의미를 분리하기

PyTorch allocated·reserved와 NVML 관측 메모리는 서로 다른 지표입니다. GPU index 대신 UUID를 사용한 관측 수정과, 잘못된 이전 관측값을 비교에서 제외한 과정을 기록했습니다.

실험의 경계

4월 ImageNet, 5월 ViT 비교, 8~9월 KubeRay 언어모델 실험은 서로 다른 실행입니다. 모델·GPU 수·토폴로지가 다른 결과를 하나의 개선율로 합치지 않습니다. 데이터 규모는 연구 문서에 기록된 값이며 상용 서비스 운영 실적이 아닙니다.

02 / DATA ANALYSIS

측정 결과를 판단의 근거로

실험 조건, 반복 수, 데이터 품질을 함께 확인

DBLAB · KubeRay 대표 프로젝트의 분석 결과 · 2026년 8~9월 자료

분산 실행의 시간·메모리 비교

동일한 대칭 2+2 GPU 조건의 text-QLoRA 실험에서 실행 방식과 입력 경로를 비교했습니다. 외부 실행 시간, step 시간, GPU 메모리를 각각 구분해 해석했습니다.

관측 결과

DataLoader 조건에서 보고된 PyTorch peak는 DDP 20.62 → FSDP2 15.81 GiB/GPU로 감소했습니다. 반면 평균 step은 0.911 → 17.898초로 증가해 메모리와 속도의 상충 관계가 나타났습니다.

검증과 한계

네 조건의 외부 시간 평균을 성공 실행 로그와 대조했습니다. Ray Data FSDP2는 학습 결과 5회 중 외부 타이머가 있는 3회만 시간 통계에 포함했습니다. step·메모리는 원 보고서 집계값이며 모델 품질 우위를 의미하지 않습니다.
